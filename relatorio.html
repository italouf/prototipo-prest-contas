1. Objetivo do projeto

Desenvolver uma plataforma web para gestão do Programa QuIIN, permitindo acompanhamento mensal de indicadores físicos, financeiros, estratégicos e operacionais, com foco na prestação de contas à Embrapii e no apoio à liderança interna.

O sistema deve permitir que a coordenação operacional visualize, de forma consolidada e segregada por pilar, os indicadores necessários para a reunião mensal com a Embrapii, para o BI interno e para reportes ao MCTI.

1.1. Finalidade principal

  • Apoiar a prestação de contas mensal à Embrapii;
  • Reduzir o esforço manual de consolidação de dados;
  • Garantir rastreabilidade de quem preencheu, alterou ou aprovou informações;
  • Oferecer visão consolidada e por pilar;
  • Evoluir para módulos de talentos, processos, funil comercial e governança.

1.2. Diretriz de produto

A solução deve começar simples, atacando a dor mais urgente: consolidação mensal de indicadores e prestação de contas. A recomendação é iniciar com um MVP funcional e evoluir por módulos, evitando tentar implementar todos os requisitos simultaneamente.

2. Contexto e problema

O QuIIN é um centro de competência acompanhado pela Embrapii e reportado ao MCTI. Mensalmente, a coordenação operacional precisa apresentar o andamento do centro com base no mês de competência anterior. Por exemplo, em uma reunião de julho são apresentados os dados de junho.

A reunião mensal com a Embrapii ocorre geralmente na segunda quinzena do mês, após o dia 15. Os indicadores apresentados alimentam o BI da Embrapii e suportam avaliações sobre o desenvolvimento dos centros de competência.

2.1. Dores identificadas

  • Consolidação manual mensal de indicadores financeiros e de entregáveis;
  • Dependência de planilhas pesadas e sensíveis;
  • Necessidade de montar apresentações manualmente;
  • Baixo rastreio de quem atualizou cada dado;
  • Controle descentralizado por pilares;
  • Dificuldade de visualizar cenário consolidado e segregado;
  • Esforço repetitivo para extrair dados financeiros antes de reuniões;
  • Necessidade de atualizar mensalmente kanban estratégico, destaques e indicadores.

2.2. Contexto financeiro

O programa recebeu R$ 60 milhões para criação do centro de competência, distribuídos entre pilares:

Pilar Valor previsto Observação
PDI / FCCT R$ 29 milhões Projetos de pesquisa, desenvolvimento e inovação
Formação e Capacitação de RH R$ 14 milhões Cursos, turmas, matrículas e pessoas formadas
Infraestrutura R$ 10 milhões Aquisições, obras, equipamentos e adequações
Atração e Criação de Startups R$ 7 milhões Programas de startups, times e projetos

Além do recurso Embrapii, o programa possui metas de sustentabilidade por meio de Associação Tecnológica e Outras Fontes.

Fonte Meta de captação Observação
Associação Tecnológica — AT R$ 7,75 milhões Captação junto a empresas privadas e parceiras
Outras Fontes R$ 6,3 milhões Editais, Fapesp, Finep, Senai Cimatec e investimentos comprováveis
Total de sustentabilidade R$ 14,05 milhões Soma das metas de AT e Outras Fontes
Regra importante: a Embrapii considera execução financeira como o valor efetivamente gasto/comprovado, não apenas o valor captado ou previsto. Além disso, renovações de associados podem contar para captação/receita, mas não contam para a meta de quantidade de CNPJs novos.

3. Produto proposto

O produto proposto é um Portal de Gestão e Prestação de Contas do QuIIN, acessível via navegador, com controle de acesso por papéis e visibilidade por pilar.

8. Regras de negócio críticas

Código Regra
RN-01 A prestação de contas mensal considera o mês de competência anterior. Ex.: em julho apresenta-se junho.
RN-02 A reunião mensal com a Embrapii ocorre normalmente na segunda quinzena, após o dia 15.
RN-03 Os indicadores alimentam o BI da Embrapii e reportes ao MCTI.
RN-04 Indicadores devem ser comparados com metas acumuladas e/ou mensais.
RN-05 Execução financeira considera o valor efetivamente gasto/comprovado, não apenas previsto ou captado.
RN-06 Os pilares possuem orçamentos distintos e devem ser acompanhados separadamente.
RN-07 A Associação Tecnológica possui meta própria de captação e não recebe recurso Embrapii.
RN-08 Renovações de associados podem contar para captação/receita, mas não contam para a meta de quantidade de CNPJs novos.
RN-09 O sistema deve diferenciar empresas novas, renovações, negociações, contratos e distratos.
RN-10 Projetos plurianuais devem reconhecer apenas a execução anual correspondente.
RN-11 Dados financeiros sensíveis não devem ser expostos em sua forma bruta para usuários sem permissão.
RN-12 O fechamento mensal deve gerar snapshot histórico.
RN-13 Toda alteração relevante deve registrar usuário, data, valor anterior e valor novo.
RN-14 Metas devem ser configuráveis, pois podem mudar ao longo do programa.

10. Arquitetura da solução

10.1. Arquitetura recomendada

A arquitetura recomendada é um monólito modular em Django, organizado por apps de domínio. Essa abordagem reduz complexidade operacional, acelera o MVP e permite evolução posterior para API ou serviços, se necessário.

10.2. Stack principal

Camada Tecnologia recomendada
Linguagem Python 3.12+
Framework backend Django 4.2 LTS ou 5.x
Banco de dados PostgreSQL 15/16
Frontend inicial Django Templates + Bootstrap 5 + HTMX
API futura, se necessário Django REST Framework
Relatórios PDF WeasyPrint ou wkhtmltopdf
Excel/CSV openpyxl / pandas / django-import-export
Tarefas assíncronas Celery + Redis
Servidor de aplicação Gunicorn
Reverse proxy Nginx
Infraestrutura Servidor interno/ET, preferencialmente Linux/Docker

10.4. Estratégia para dados financeiros

Como as planilhas financeiras possuem dados sensíveis, a recomendação é importar apenas uma planilha consolidadora, gerada a partir das planilhas originais. Essa planilha consolidadora pode ser produzida manualmente ou por script/macro Python.

Etapa Descrição
1. Planilha sensível Permanece restrita à liderança
2. Consolidação Script/macro extrai apenas valores necessários para o portal
3. Arquivo consolidado Contém competência, pilar, indicador, meta, valor e observação
4. Upload no portal Sistema valida layout e período
5. Auditoria Registro de usuário, data e arquivo importado

12. Stack tecnológica recomendada

A stack recomendada é Python + Django + PostgreSQL, por produtividade, manutenção simplificada, bom controle de acesso, facilidade para relatórios e forte suporte à manipulação de planilhas e dados.

12.1. Justificativa da escolha

  • Django possui autenticação, autorização e proteção CSRF nativas;
  • O Django Admin pode acelerar o backoffice inicial;
  • O ORM facilita modelagem de indicadores, metas, períodos e auditoria;
  • Python é forte para manipulação de planilhas e dados;
  • A stack é adequada para sistemas internos com formulários e relatórios;
  • Permite evoluir para API REST sem reescrever o sistema.

12.2. Prós e contras

Aspecto Avaliação
Produtividade Alta, especialmente para CRUD, admin e relatórios
Manutenibilidade Alta, se o projeto for organizado em apps por domínio
Controle de acesso Nativo, podendo ser complementado com permissões customizadas
Manipulação de dados Muito forte com Python, openpyxl e pandas
Comunidade Python e Django possuem comunidades grandes e maduras
Deploy Requer validação com ET/TI; recomendado Linux/Docker
Frontend avançado Pode começar com templates/HTMX e evoluir para API/React se necessário
